# CTX3 `.tex` 格式取证与本地转换（2026-10-28）

本记录基于本机真实解码样本，且不包含原版像素或二进制。另一个 ChatGPT 会话已在完整原包中对 1942 条 CTX3 资源验证字符串表；纹理载荷结构目前只在已列出的样本和本地实验中确认。

## 已确认的纹理路径

三个样本均含 17 条 CTX3 字符串，其中观察到的纹理属性包括：

`linear`、`minfilter`、`magfilter`、`clamp`、`wraps`、`wrapt`、`id`、`format`、`r8g8b8a8`、`sizex`、`sizey`、`sizez`、`hasalpha`、`type`、`texture2d`、`mips` 和 `datasourcepath/...`。

字符串表后存在 `DATA` 段。在三个样本中：

- `DATA+0x04` 是 8 字节属性记录数量 `M`；
- `DATA+0x08` 是二进制分组数量 `N`；
- `DATA+0x0C` 为 0；
- `DATA+0x10` 是 payload 字节数；
- 随后依次是 `N+1` 个分组偏移和 `M×8` 属性表。
- 三个纹理样本均为 26 条属性记录、1 个分组，因此 DATA 头长 `20 + 4×2 + 8×26 = 236` 字节；
- 宽度和高度通过字符串序号找到 `sizex`/`sizey` 键及其后续值记录，分别得到 256、256、16 和 32、128、8；
- DATA 头之后是自上而下观察到的存储像素区；
- payload 长度均等于 `width × height × 4`；
- 像素字节为 `r8g8b8a8`；
- payload 后恰有 16 字节，等于此前全部文件数据的 MD5；
- 生成 PNG 时需上下翻转，才能恢复正向方向。

三个样本的人工查看结果分别与源路径相符：透明噪点菜单纹理、水乡背景和黄色 HUD 圆框。尺寸结论由 payload 长度、头部字段、像素连续性和可视结果共同支持。

2026-10-30 又从完整原包只读导出主菜单与练习模式两张背景：

- `BL_GUI_backgrond_mainmenu.tex`，SHA-256 `273efbf7475cf802710a12e5202dc0cb7a5fcf872cc3beffd8316e7c03340ceb`；
- `BL_GUI_backgrond_practice.tex`，SHA-256 `7827e63474fadc7c59c969576b4f1ae82d63722c3bfac8cd521abd0950513f19`。

两份资源均为 512×512 `r8g8b8`、26 条属性记录、1 个 786,432 字节 section，恰好等于 `512 × 512 × 3`，尾部仍为 MD5。`mips` 值记录为 `(0x40000001, 1)`，只声明一个 section；这不同于已观察的完整 RGBA/ATC mip 链，因此转换器把 `r8g8b8` 限定为已验证的单层描述。其唯一 section 描述字为 `0x40640000`；同字段在 RGBA 与 ATC 样本中分别是 4/8 字节 stride，但 `r8g8b8` 的掩码字段 `0x00640000` 尚未解释为 stride 值 50，因此转换器只校验完整观察标记，不虚构其业务含义。转换时按紧邻 RGB 三元组展开为不透明 RGBA（alpha=255）。

两份 `r8g8b8` 的原始行序均为 top-down：直接保留行序时，主菜单图恢复 Bruce 向右踢击、练习图恢复 Bruce 伸手的直立画面；额外上下翻转会让人物倒置。因此转换器把方向记录为 `top_down`，默认不再翻转；既有 RGBA 样本记录为 `bottom_up`，默认仍翻转。这里的方向结论来自两张真实图片的人工查看，不声称所有 `r8g8b8` 资源必然同样排列。

当前转换器仍根据 DATA 计数计算头长，不再假定固定 236 字节。2026-10-30 已在本机三份 Brick Davis 1024×1024 `.tex` 上只读验证 mip 打包：

- `5c4dc7f7333f7fc62ae1229fbcdc0f58e877fb1d.tex` 为 `r8g8b8a8`，DATA 记录数 36、分组数 11、payload 5,592,404；11 层字节数为 `4194304,1048576,262144,65536,16384,4096,1024,256,64,16,4`。基础层是前 4,194,304 字节。
- `19820ad048bfb97f17e3d9bd4118004252bf273f.tex` 和 `00b10ae060e9dc141268c2fc23f46a7e69403a5e.tex` 均为 `atc_rgb`，payload 699,064；11 层字节数为 `524288,131072,32768,8192,2048,512,128,32,8,8,8`。基础层是前 524,288 字节，按 4×4 ATC RGB 块解码为 4,194,304 字节 RGBA。
- 三份资源的 `mips` 键后一条记录都是 `(0x4000000b, 1)`，随后 11 条数组描述分别引用 section 0–10。描述中的 stride 分别为 RGBA 的 4 字节和 ATC 的 8 字节；元素数与各层尺寸及块数一致。小于 65,536 的元素数完整保存在低 16 位，基础层的 65,536 或更大元素数按已观察的 16 位字段存储为 0。
- 三份资源末尾 16 字节都等于此前全部字节的 MD5。转换器只读取输入；PNG 先写入同目录临时文件，校验后以不覆盖的 `os.link` 发布最终文件，失败时删除临时文件。

ATC RGB 解码按标准 8 字节块实现：前两字小端读取，颜色 0 的 bit 15 选择模式，其余位为 `R5/G5/B5`；颜色 1 为 `R5/G6/B5`；后 4 字节是 16 个 2-bit 索引。四色模式使用 `5/8` 与 `3/8` 插值，另一模式使用黑、`max(0, p0-p1/4)`、`p0`、`p1`。算法参考 Perfare 的 [AssetStudio `atc.cpp`](https://github.com/Perfare/AssetStudio/blob/master/Texture2DDecoderNative/atc.cpp)（MIT；当前 15,590 stars，仓库已归档）。代码按该算法重新实现，没有复制源文件。Khronos 扩展没有公开完整解压公式，原版 Adreno GPU 逐像素结果也尚未对照，因此像素解码仍是高置信度实现候选。

## 本地转换

```powershell
python -X utf8 tools/tex_convert.py "C:\path\to\decoded\texture.bin" --output "$env:LOCALAPPDATA\BruceLee-PC-Port\previews\texture.png"
```

输出必须是新文件，并位于仓库外和可识别的同步目录之外。工具不会修改输入的 CTX3 数据，只读取并在写 PNG 前验证字符串标识、DATA 边界、尺寸、payload 长度和 MD5 尾部。

2026-10-28，本机三个真实样本分别在 MXC 沙箱内完成解析和 PNG 编码，均返回成功；该过程未把原版像素提交到 Git。完整 Python 测试集共 44 项通过，覆盖 CTX3 标识、通用 DATA 头边界、MD5、尺寸、PNG 行翻转、覆盖保护、项目目录保护和 CLI 报告。

## 尚未解决

- 三个早期样本不能证明所有 `.tex` 都使用相同的 236 字节 DATA 描述；Brick 的三份 1024×1024 样本使用 356 字节 DATA 头。
- 当前只验证了 `mips = (0x4000000b, 1)` 后紧跟完整 2D mip 描述数组的样本。其他 mips 记录布局仍不支持。
- `sizez`、`hasalpha` 的完整语义以及 ATC 在原版 Adreno 设备上的逐像素结果仍未闭合。
- 纹理转换成功不等于模型、骨骼、动画、材质绑定或最终渲染已经验收。
